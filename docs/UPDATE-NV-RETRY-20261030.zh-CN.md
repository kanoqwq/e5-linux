# 更新失败后的 NV 备份重试

## 故障和实机证据

畅行60从 `g788fa1ad` 安装包更新时，NV 备份报 `NVError: nv_busy`，随后原机 NV
恢复也报相同错误。错误发生在提交更新、写 boot 之前。

原更新准备已写 `/.e5-update/request.ready`，随后查找 UFS boot 失败；未执行到
把该文件发布为 `request` 的步骤。实机只读检查确认：旧的 `request.ready` 仍在，
没有 `request`。NV 的 maintenance_lock 在已经取得两把真实锁后，单凭 ready 文件
存在就拒绝备份，形成“前次失败 → 备份不能重试 → 更新不能继续”的闭环。

宿主更新器还把所有备份异常都当成工作 NV 损坏，忙、连接中断及程序错误也会
转入原机恢复。这是第二个缺陷，导致最终提示与实际原因不符。

## 修复边界

只读的 CLI NV 快照允许在仅有 `request.ready` 时执行，便于重新准备更新。
仍必须取得原来的两把 inode 锁，且已激活的 `request` 仍会阻止操作。
网页同步、写回等操作保持原来的互斥规则。不删除锁文件，不删除旧的准备记录，
不使用超时强拆，不覆盖原机 NV。

宿主仅对已识别的工作副本校验／来源异常提供原机 NV 恢复选项。
忙直接提示等待正在执行的操作；连接、程序及其他异常保留真实错误，不再尝试
读取另一套 NV，也不弹错误的覆盖确认。原机恢复仍需单独校验和用户明确同意。

快速刷新入口同时更新外部 NV 辅助程序及 `scripts/tools/e5-update.py`，
防止源码修复没有进入安装包。完整组装还会将修复同步进系统自身 NV 模块。

## 验证

- NV 回归共47项通过，含真实子进程 CLI 快照、保留 ready 后连续两次备份、
  真实锁占用和已激活请求的拒绝、物理源和工作文件不变，以及禁止错误回退。
- 宿主备份回归执行实际 NV CLI、压缩归档、下载哈希校验和 PC 记录，不模拟掉备份。
- 2026-10-30在用户连接的畅行60上，保留故障现场的 ready 文件，实际执行新版
  `save_nv_backup` 成功，压缩备份7,198,536字节；没有原机恢复回退。
  boot 写入前置检查成功解析 Linux boot `/dev/sda39`、misc `/dev/sda3`。
- 该实机检查仅上传临时检查脚本、生成只读快照并保存 PC 备份；没有写 boot、
  原始 NV 或工作 NV 内容，没有修改 IMEI，没有重启。它不等同于离线刷写验收。

详细现场及备份留在本机 `work/cx60-update-nv-retry/`，不作为生产构建输入。
