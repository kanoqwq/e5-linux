# T551M 充电后显示停在 0% 的实机处理

## 实测事实

2026-10-18 连接的设备经 `/etc/e5/device-profile=t551m` 确认。
运行内核 `6.18.54-t551m-otg10-g020b970e351e-dirty`，尚未部署本仓库
`5c8e3bb4` 新增的低电量关机接管。

重启前 uptime 约 18251 秒：

- `battery.capacity=0`，状态 `Charging`、`capacity_level=Low`。
- `sc27xx-fgu.capacity=635`（厂商接口以千分比表示，即约 63.5%）。
- 电池端电压约 3.975 V，电流约 +72 mA；当时连接电脑 SDP，输入限制 500 mA。
- 后续读取 FGU 继续从 635 升至 636；近期日志存在 FGU 周期计算，但没有 CM 的 `vbat:...soc:...` 更新日志。
- 系统 suspend 成功/失败计数均为 0。

因此不是单纯屏幕缓存，也不是充电完全没进去；CM 对外显示状态与运行中的 FGU 分离。
FGU 的 63.5% 是驱动估计，不以电压推算的数值冒充准确实测容量。

## 与原厂路径的关系

T551M 原厂 `sprd-charger-manager.ko` 的 `cm_shutdown_handle` 反汇编见
`docs/LOW-BATTERY-STOCK-20261018.zh-CN.md` 对应证据。
Android 模式调用 `cancel_delayed_work_sync(cap_update_work)`、将 UI cap 置零，
再发 `power_supply_changed`，原本由 Android 上层继续关机。

旧 OpenWrt 没有该接管。若触发该分支却继续运行，FGU 可继续积分，CM 更新任务则已停止，
后续充电不自动恢复这项任务。本次的状态与该路径相符，但首次欠压时的日志已经被覆盖，
不能把这一触发链写成已完整抓到的事实，也不能排除其他停止 CM 更新的原因。

新增服务按原厂 Critical/充电例外接管正常关机；充电时驱动明确上报 Low，
不会仅凭显示 0% 强制关机。没有为恢复显示而改成 UI=FGU、写 calibration 或强制校准。

## 本次实际操作

- 仅部署已提交的 `unisoc-battery` 六个 ucode 模块、procd init 和 power_supply hotplug 入口，逐文件 SHA-256 校验；启用并确认实例运行。
- 设备备份目录 `/root/update-backups/battery-guard-20261018-192849`。
- 下发正常 `reboot`，让已有 CM 更新任务重新初始化；没有强制复位、写 misc、切槽、写 NV 或直接改写电量计。
- 未替换内核/驱动/Android，不改电流、JEITA、容量表或平滑速度。
- 重启后约 49 秒，显示恢复至 2%，FGU 为 639，电压约 3.964 V；重新出现 CM 周期 `vbat:...soc:639,10,...` 日志，证明更新恢复。
- 约 84 秒再次读取已到 4%，FGU 仍为 639；procd 实例运行、开关机链接齐全，WAN 已正常连接。
- 显示与 FGU 的差值仍需原有平滑过程消化。恢复更新不等于已经恢复到准确百分比，不能写成整个电量估算问题彻底解决。
