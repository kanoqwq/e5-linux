# SIPA 接收补充与发送回收等待修正

日期：2026-11-14。线索来自
[上游 issue #498](https://github.com/dikeckaan/mu300-linux/issues/498)。
`0x10000` 是完成描述符错误事件，不能仅凭旧日志中的 overflow 字样
认定接收环已满。以下修正针对实际 C 函数中复现的条件性缺陷，
没有把它们认定为 issue 中那次断流的唯一根因。

## 实现范围

- MU300 的 6.18／7.2 共用 `upstream/modules/sprd_modem/sipa_v3`。
  回收线程仅在有完成项，或待通知且空位超过原有恢复阈值时运行。
  空完成队列仍会检查迟到的流控请求，解决空位已归还却漏发恢复通知的情况。
  挂起期间保持等待，原有恢复入口重新唤醒线程。
- 三个仓库的运行期接收补充路径配对释放失败提交的 skb／DMA 映射。
  软件所有权队列入队成功后才发布硬件描述符；失败时保留未补充数量，
  后续沿原有补充流程重试。页缓冲只对构造成功的 skb 增加引用。
- Pro 原有 `build_skb` 失败检查保留，不重复添加。E5 通过共享
  `sipa-buffer-lifecycle.patch` 和 `sipa.py` 接入现有各机型准备流程，
  覆盖已登记的移动版及 legacy 内核来源；不是仅修改本地准备树。

正常提交格式、队列深度、实时线程优先级和硬件省电策略保持原有约定。
没有新增周期轮询、自动清空队列、强制重拨、错误包重发或 AT 通道变更。
本次集中修正运行期补充；没有扩展为初始化分配流程或硬件错误恢复的重写。

## 离线验证

`sipa_receive_buffers.c` 直接运行生产接收函数，覆盖三条补充入口的正常提交、
32 项批次边界、分配失败、映射失败、描述符不可用、所有权队列满、
部分提交及失败后重试。检查发布数量、待补充数量、skb 和 DMA 释放，以及页引用。

MU300 线程测试覆盖初次资源恢复前不读 MMIO、零完成／低空位时阻塞、
迟到恢复通知、阈值边界、重复唤醒、挂起／恢复和线程停止。
原有 TX BUSY 重试和校验和回归继续通过。

Pro 的接收用例、12 项既有资源通知／队列次序回归，以及来源摘要检查通过。
E5 在两套已登记源码上验证共享补丁链的干净应用、旧状态升级、重复应用，
并通过接收补充、发送完成、资源请求／释放和 Ethernet／USB 队列次序回归。

旧 MU300 函数在映射失败、所有权队列满、页 skb 分配失败三个对照中
触发新用例的断言，修正后的生产函数全部通过。接收用例启用 ASan／UBSan。

以上不是完整 ARM 内核构建或硬件验收。本轮没有刷写、热部署、重启或拨号。
已有固件 ZIP 尚不包含这些改动，发布前需重编匹配的内核／模块。
