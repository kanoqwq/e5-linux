# 充电时显示电量不增长：公共修复与 E5 实机证据

## 故障与证据

2026-10-21，连接的 E5 运行 `6.18.54-e5-mobile4`（Oct 19 21:53:28 +08 构建）。
用户观察到接充电器一直为 5%，换到电脑 USB 才增长。
完整原始日志保存在本机忽略目录 `out/diagnostics/e5-soc-20261021/`。

充电器 DCP 阶段，401 次连续采样覆盖 54 分 37 秒：FGU 估算从 692/1000
上升到 991/1000，电池充入电流曾达 1.4–1.7 A，CM 显示始终是 50/1000。
CM 定时更新仍每约 8.19 秒运行，内核未发生系统 suspend。
相应温控日志反复为 `jeita status1:(4) 2 2`、`charging_status 1`，
即实际温度所在区及恢复区均为 2，旧状态却卡在 4（过热）。
CM 因而报告 Not charging，电量平滑的非充电分支禁止显示值上升。

切到电脑 SDP 后，CM 重新使能充电，状态恢复并进入满电显示平滑。
显示值每次更新约追赶 1%，不是几分钟内实际充入相同电量。
本次没有通过直接覆盖 SOC 来使显示追上电压。

## 原厂参照

参照的是本机留存 Android 13 固件
`UNISOC/ums9158_1h10_cmcc/ums9158_1h10:13/TP1A.220624.014/2024112822:user/release-keys`。
从留存 vendor_dlkm 镜像只读提取，不挂载实机 Android 分区。

| 原厂模块 | SHA-256 |

| sprd-charger-manager.ko | `45dd82b92ff16626ccac77fe802c06fccdd3eda68ba0175b17a41c9a0f828d07` |
| aw322xx-charger.ko | `76a7ce1d9eb999e0d575ba63a6907a283cc124275f8fac46c8ff8f84bb62dc10` |

原厂 `cm_manager_get_jeita_status` 的 0x2e3c–0x2e74 将初始区域设为 0、
温度参考设为 −200（十分之一摄氏度），再执行原厂滞回分类。
移植源码采用区域 4、参考 250，并叠加首次读取时直接返回所在区域的修补。
公共修复恢复原厂初始化和分类流程，移除该叠加捷径；正常区、低温区、高温区、
恢复阈值、电流及电压继续取本机设备树。没有关闭温控。
这解释并修正了错误初始状态；原日志不包含首次变成该状态的完整调用链，
不能把某个并发入口或温度瞬变进一步写成已证实的唯一上游触发点。

## 修复的边界

### 1. 公共 JEITA 初始化

`charger-jeita-state.patch` 通过 `devices/common/fuel-gauge.py` 接入已有公共栈。
E5、T551M、M8、T512N、远航 41S、守护宝 K1 及调用同一准备器的后续机型取得修复。
保留冷热保护、恢复滞回、连续确认以及原厂 SOC 平滑。

### 2. 公共 FGU SET 命令不能因相同数值被省略

本次还抓到两次实际保存失败：UI 请求 130 回读 0；normal 请求 1000 回读 0。
两次均以 `-EIO` 向上传播。

随后使用独立、短时 regmap trace 实例观察自然更新，并通过既有 CAPACITY 保存接口
重复保存已经自然达到的 100% UI；未使用 CALIBRATE，也未写不同百分比。
30 次保存最终均返回成功，但原始跟踪实际捕获一次 normal 首次回读 `a000`，
第二次尝试才回到 `a064`。该事务只有 CLEAR 写入，SET 寄存器读到相同的 `64`
后，regmap 的普通 update 跳过了 SET 写入。

`fuel-gauge-set-latch.patch` 仅将三个保留字段的 **SET 阶段**改为
`regmap_write_bits()`：仍执行 masked read-modify-write、保留其他位，但保证发出
SET 命令。CLEAR 阶段继续使用原有 masked update，200–210 μs 时序保持不变。
这与之前把所有 SET/CLEAR 阶段都强制写入的尝试不同。
原厂二进制采用 masked update；这里的修正依据是本机实际总线跟踪显示出的
Linux regmap 省略命令现象，不冒称原厂调用了 force=true。

### 3. E5 AW32257 专属状态同步

原厂 `aw322xx_start_charge` 0x2474 清除 REG01 的 CE/HiZ/boost 三位，
stop 路径 0x23c8 设置 CE。E5 适配中恢复同样的启动位操作，并传播 PMIC/I2C 错误。
明确的停充命令会到达硬件，不能因为缓存标志已是 false 就直接跳过。
成功完成操作后才更新缓存状态；CALIBRATE 的使能回读读取实际控制位。
属性读写按照原厂方式持有驱动 mutex，错误返回也会释放锁。

该修复只进入 E5 的 AW32257 准备器。其他五款使用 BQ/SGM 各自驱动、PMIC 门控与
板级电压/电流映射，未套用 AW 的寄存器位。

## 离线验证

- `test_charger_jeita.py`：579 个暖启动温度、真实过冷/过热、恢复滞回及换充电类型。
  另覆盖连接 E5 实际 DT 的 549 个正常启动温度；其温区边界为 0/15/45/55°C。
- `test_fgu_latch.py`：两组保留区的全部 1001 个合法 SOC，每值连续保存三次；
  保留启动位、错误传播，并确认旧的省略 SET 实现会被测试复现并拒绝。
- `test_fuel_gauge.py`：已有 4096 编码、恢复、保存错误、最终关机顺序、容量算术及
  准备器幂等/原子校验继续通过。
- `devices/e5/test_charger.py`：原厂电流编码、USB 预算、缓存失步时的真实停充、
  启动控制位、总线失败与 mutex 释放。
- 41S 的硬件满电补丁通过其原有 restore/apply 顺序与公共补丁组合，未覆盖其硬件终止规则。

这些离线验证和编译不等于其他机型已完成实际充放电测试。
