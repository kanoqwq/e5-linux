# 接听失败后错误丢失通话状态

## 实机现象与证据

2026-10-20，angelcare K1 的 `V1.0.1-B7` 基带，用户报告连接蓝牙时按实体接听键，电话已接通，但界面消失、音频及其他操作异常。19:49:39 的日志记录 incoming-new；19:49:41 接听请求后，MM 将对象从 ringing-in 改成 terminated/error。19:49:44 起，基带通话列表仍报告相同来电 ACTIVE，MM 因原对象已结束而打印 unexpected incoming call，无法恢复原界面及音频观察链。

用户随后两次接听正常。详细日志也记录了 19:51:16、19:51:32 的卡寻址接听命令成功、对象转 ACTIVE，挂断后按原有空列表复核正常结束。这两次发生在本修复部署之前，只能说明问题具有间歇性，不能作为修复验证。

第一次失败只有 INFO 日志，无法证明究竟是 AT 错误、回复解析还是其他命令完成错误；也不能断言蓝牙接听键是触发条件。能够确认的是：接听操作失败被误当成了底层通话已经结束。原始日志含电话号码，保存在 git 忽略的 `work/k1-bluetooth-call-20261020/`，不纳入发布载荷。

## 共用后端修复

新增 `modemmanager-21-unisoc-accept-failure.patch`，仅对已经使用 `e5-dual-sim-voice` 的共享 Unisoc 后端修改 `handle_accept_ready` 的错误分支：保留原通话对象及现有状态，由原有按卡 CLCC 快照继续确认。不能把一次命令失败直接宣布为 TERMINATED；也不把失败包装成成功。

原始错误继续返回 GUI 或 HFP 操作方，不自动重复 ATA，不增加 AT owner、轮询、复位或任意等待。CLCC 已先更新 ACTIVE/HELD 时不覆盖；已经真实结束时也不复活。原有正常接听、来电有效期、成功状态及其他 modem 插件路径保持原行为。本次没有修改 UI 的关闭条件，也没有让已经结束的通话窗口强制保持显示。

修复经同一补丁集合进入 Debian 和 OpenWrt 的公共构建路径，不增加 K1 型号判断。OpenWrt E5REV 升至 37，新测试加入实际 APK 编译后的回归和源码哈希清单。MU300 使用自己的 AT 后端，检查其接听入口未发现该 MM 错误结束分支，本次不向 MU300 加入不适用的 MM 补丁。

## 自动化验证

`openwrt/tests/voice-accept.py` 抽取真实生产完成回调，用假的 AT 结果、D-Bus 调用和计时器验证：失败保留 RINGING_IN/ACTIVE/HELD，真实 TERMINATED 不复活，错误原样传回、只释放一次操作上下文；失败不取消原来电有效期，正常成功保持原状态与计时器清理，非 Unisoc 保持原错误行为。没有拨打或接听真实电话。

已对修补后的生产源码运行新测试、原通话身份/按卡路由和挂断回归，均通过。隔离的 OpenWrt 交叉编译生成 `modemmanager` 与 `modemmanager-rpcd 1.24.0-r945`，完整构建中的 SIM、电台策略、通话恢复/挂断、短信隔离、移动重连和端口匹配回归均通过；源码/APK 清单校验通过。没有覆盖其他任务使用的构建缓存或重建整包。

通话事件推送与过期 HTTP 回退测试通过。额外运行 VoLTE/VoNR 开关测试时，发现旧测试夹具没有注入页面已依赖的 AutoMode 模块，导致 ReferenceError；补齐该独立组件的惰性 mock 后，原有双向开关、确认、忙状态、失败、SIM 范围及多语言断言通过，没有改动实际网络设置页面。

## 部署与实机验证边界

核对原机 profile/eMMC 身份、确认没有通话后，备份旧软件包文件、数据库及网络配置，仅更新 K1 的上述两个 APK 并重启 ModemManager。启动时遇到旧 MM 尚未释放 D-Bus 名称、新实例提前退出的已有重启时序问题；确认旧进程已经退出后重新启动 wrapper，服务恢复。未重启整机、改分区或单独发送无线复位命令。

部署后 MM 为 connected、home、PS attached，netifd WAN up 且非 pending，通话观察服务 available。原网络配置与备份逐字节一致，K1 AOL 听筒接线仍在，9 个原厂 NV 及全部工作设备校验通过。原文件备份位置记在 git 忽略的 `work/k1-bluetooth-call-20261020/mm-upgrade.json`。临时 DEBUG 捕获已经结束，日志级别恢复 INFO。

部署后没有由代理主动拨打电话，用户也尚未反馈修复版的通话复测；当时蓝牙已断开。本次确认的是公共错误分支修复、自动化回归和实机服务恢复，不宣称已在硬件上再次触发并验证该偶发错误，仍需后续通话观察。
