# M8 长时间运行后的屏闪报告

## 证据与范围

2026-11-11 群友报告 VIPME M8、OpenWrt 25.12.5、6.18.54、TF 安装，
约三小时后反复出现寄存器 0x0A 读值 0 与 ESD 恢复。其将本机 DTBO 的
ESD 开关由 1 改为 0 后，报告 18.7 小时未再闪屏。这是贡献者的观察，
本地没有该机故障日志、当前设备树或同批实机，不能确认全部因果链。

本地 `dumps/m8-stock` 保存的 Android 13 原厂资料为
`eng.wangqi.20240118.131916`，指纹
`UNISOC/ums9157_2h10_native/ums9157_2h10:13/TP1A.220624.014/wangqingpeng01181306:user/release-keys`。
其启动参数选中 `lcd_st7796u_yihua_mipi_hvga`，对应面板的
`sprd,esd-check-enable` 为 0；同一设备树还含其他面板节点及不同配置。
不能用该原厂资料证明群友机器也应采用相同值，更不能把其分区偏移移植到其他固件。

## 已确认的代码问题与修正

M8 的 6.18 适配尚未调用已存在的 DSI FIFO 修正：两个等待函数以 0
表示成功，旧的 `!(cmd && payload)` 会误报，并在命令 FIFO 正常时跳过
payload FIFO 等待。M8 现在通过自身 prepare 入口调用该修正。

另外，DSI 接收忽略等待响应超时；ESD 读取忽略最大返回长度设置及 DCS
读取结果，可能将未读到的初始 0 当成有效状态值。现在返回真实传输错误，
只有完整读取一个字节后才比较面板状态；各退出路径释放原有锁。

改动仅在 `recipient == 'm8'` 时应用。保留设备原有 DT/DTBO、ESD 开关、
模式、周期、寄存器和预期值，保留真实异常时的原恢复流程，不写 DTBO。

## 验证与限制

`devices/m8/test_display_esd.py <kernel>` 在临时目录对真实驱动函数应用
补丁并编译运行，覆盖 FIFO 成功／失败、响应超时、短读、正确状态、错误
状态、关闭／休眠路径及锁平衡，验证重复 prepare 不会重复插入。
同一测试已接入 M8 的版本控制构建入口。

这些离线检查不能证明三小时后的实机故障已消失。本次没有刷机、修改用户
分区或完成长时间硬件验收；需使用重新编译的 M8 内核复测。
