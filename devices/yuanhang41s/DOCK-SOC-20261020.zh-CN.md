# 41S 扩展坞与电量快速下降记录

2026-10-20；原厂版本、模块哈希与表格来源见 README / POWER-CHARGING。
用户确认普通 OTG 与供电可用，报告实验性主机受电模式未奏效、百分比快速下降。
本次读取现有日志，没有为了采样重连蜂窝、修改电流上限或改写 SOC。

## 已确认：显示下降远大于真实库仑变化

同一启动周期，约开机 36–618 秒：

| 读数 | 开始 | 结束 |
| --- | --- | --- |
| UI 电量（charger-manager） | 52.1% | 34.6% |
| FGU 原始 SOC | 10.5% | 10.3% |
| 电压 | 4.244 V | 4.231 V |
| OCV | 4.255 V | 4.240 V |

约 331–618 秒的插拔/扩展坞区间，UI 从 50.6% 下降到 34.6%，原始 SOC
从 10.7% 到 10.3%；5000 mAh 标称容量下，后者对应约 20 mAh，不能解释
前者代表的约 800 mAh。FGU 同时记录相对启动净库仑变化约 −12 mAh。
这里的数值精度与库仑量化不同，不将两者强行说成完全相等。

charger-manager 在未充电状态下按既有平滑逻辑追赶偏低的原始 SOC，日志
多次每约 8 秒下降 0.5 个百分点。重启读出的保留 UI / normal 也明显不一致：
早先为 65.1% / 8.2%，本次启动为 52.1% / 10.5%。

普通 OTG 供电期间也有真实放电，采样约 −0.5 至 −0.8 A，不能说完全没有
耗电。当前接回电脑后电压约 4.24 V、净电流接近零；短时 CPU 快照约 98%
idle、温度约 30°C，未观察到 CPU 持续满载。但没有同状态 Android 对照或
长期待机实测，不能据此宣布功耗完全正常。

原厂 Android 的历史日志原始 SOC 为 96.2%，对应 OCV 约 4.27–4.29 V。
原厂 normal 区编码反汇编再次核对：0x42b4 函数的 0x4338–0x4344 计算
`(value & 0xff) * 10 + ((value >> 8) & 0xf)`，与现驱动相同，不是把 10%
误读成 100% 的格式差异。

### 历史基准损坏的解释与边界

旧探测版本缺少本机原厂的实时 OCV / POCV 300 mV 一致性检查，可能曾用
过期的 3.517 V POCV 下调 normal 基准；当时首次读到 normal 7.6%，而
实时 OCV 约 4.2 V。该缺口已在此前修复，当前启动能拒绝旧 POCV。
这是有原厂二进制和现有日志支持的根因线索；没有保存到最初那次错误写入
前后的完整现场，不能把具体发生时刻写成已证实。

阻止再次错误校准不等于已重建历史真实 SOC。现有 normal 仍是数值合法但
明显失真的保留值。没有通过冻结 UI、向保留区写一个猜测百分比或强制校准
处理它；有效原厂 OCV / 满电恢复条件及恢复后的真实计量仍需验证。

## 已确认：扩展坞未成功进入充电链路

约 355 秒接入的普通 OTG 成功枚举 USB Hub、r8152 等设备，内核为
`role=host boost=1 external=0`。后续多次 CC sink / VBUS 存在，但 BC1.2
状态 0x1806 经重试仍返回 UNKNOWN，charger-manager 报未识别充电器，
没有获得有效充电许可。不能把“有外部电压”说成“正在充电”。

除开机约 49 秒的受控电脑对照以外，这次日志未看到后续扩展坞阶段成功
进入 `role=host boost=0 external=1`。日志没有记录每次用户选择的策略，
不能凭此断言用户没选对；新增的策略切换日志用于补齐以后这部分证据。

### 修正 Unknown 完成通知

确认了新的软件缺口：`sprd_bc1p2_notify_charger()` 对重试结束的 UNKNOWN
直接 return。主机受电模式等待 `CHARGER_DETECT_DONE`；Unknown 完成后
却没有通知，可能一直停留在 device。SDP 电脑对照不会暴露此分支。

41S 准备器现在让 Unknown 最终结果同样发出既有通知。Unknown 类型和
对应零充电许可保持原样；数据角色可收到完成事件，不假装 SDP/DCP/PD，
不因此提高电流。实际 C 回归覆盖 Unknown 完成、仍在重试、正常 SDP 与
断开通知，类型不被修改。

此修正只解决完成事件遗漏，不代表充电器识别或 PD 角色交换已经实现。
扩展坞是否无需 PD 就提供上游数据/有效充电能力，仍需该实物验证。

### 部署与回归结果

17:27 已将修正版写入本机 Linux A，并同步校验全部 237 个匹配模块；
Android B 的完整 boot 哈希与原始备份一致，100 GiB 根分区不变。
重启后，电脑 SDP 供电对照再次实际进入 data-host / power-sink，
SGM REG01=0x9a，boost 位关闭，xHCI 根集线器注册，电池保持 Charging。
测试结束恢复 auto/device，USB 双向各 8 MiB 的 SHA-256 校验通过。
这次对照是 SDP，不是对用户扩展坞 Unknown 分支的硬件验证。

本轮外网验证没有通过：SIM2 在 ModemManager 中为 idle / detached，
开机记录 No network service，WAN 没有地址或默认路由，DNS 返回 REFUSED。
模块已被识别，不是“无模组”；未为通过测试擅自切卡、改频段或重置射频。
不能把之前启动的外网测试结果当作本次回归结果。

重启后 FGU normal 仍约 10.6%，电池实际约 4.28 V，显示仍在追赶历史
基准。新 USB 事件修正没有修复这项历史 SOC，不能据此宣布电量恢复。

原始日志与表格在忽略目录 `out/yuanhang41s/acceptance/dock-battery-*`。

## 后续网络与电流复核

17:35 在公共事件恢复服务补齐 NO_DEVICE 就绪处理后，WAN 自动连接、外网
与 DNS 通过；随后正常重启也自动连通。此前失败记录保留，不覆盖历史结论。
详见 [公共恢复记录](../../docs/NETWORK-LATE-MODEM-20261020.zh-CN.md)。

同一电脑 SDP 500 mA 输入、现有蜂窝/热点配置下，分别亮屏和息屏采样
14 次，电池平均净电流约 +49.7 mA / +187.6 mA；全部亮屏样本亮度为 120，
息屏为 0，结束恢复原始屏幕状态。正号表示净充入，不能把这两个数直接
称为整机待机功耗，也不是 Android 同条件续航对照。

该窗口未观察到与 UI 快速下降相符的真实失电；后续 raw SOC 从约 10.6%
缓慢增加至约 11%，UI 仍受历史误差影响。未写入任何猜测百分比。原厂的
实际满电端点/有效静置校准仍是恢复计量的条件，当前没有满足并验证这些
条件，故历史 SOC 恢复仍明确未完成。

随后发现驱动缺少硬件 FULL 上报、CM 终止条件与本机 SGM 不匹配，已补入
本机满电端点路径，见 [后续电量修复](BATTERY-ENDPOINT-20261020.zh-CN.md)。
这不改变上面的历史观测，也不能在真实充满前将历史 SOC 恢复标为通过。
